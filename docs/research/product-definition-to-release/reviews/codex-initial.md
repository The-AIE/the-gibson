# Codex initial research position

> **Authority:** Non-normative research. This is an initial position, written before reading the external model memos. It does not change repository policy or authorize implementation, merge, integration activation or deployment.

## Hypothesis to test

For a bounded class of business software, a nontechnical owner and one primary coding agent can turn plain-language intent into an accepted specification, useful release-sized work, and a deployed capability with traceable evidence, at less total effort and no loss of required quality compared with current practice.

The phrase “description to enterprise-grade software” contains several unproven hypotheses: the description is sufficient to expose consequential unknowns; the specification preserves the owner's intent; decomposition preserves user value; an interchangeable agent can implement the result; the environment can evaluate the actual behavior; and released behavior satisfies a declared operational/risk profile. Each can fail independently. A system that generates impressive documents while shipping the wrong workflow has failed the product hypothesis.

## Wedge and differentiation

Start with bounded internal business workflows on an existing repository and supported deployment stack. The primary user is the domain/product owner, who can describe the problem and recognize a useful result but should not need to operate the development machinery. Engineering, security and operations remain accountable where their judgment or external authority is actually needed.

The differentiated candidate is an understandable, accountable bridge from intent to demonstrated outcome across existing tools. It is not another general coding model, IDE, source-control system or trace dashboard. Existing spec toolkits mean document generation alone is a weak moat; Atomic's intent/evidence graph overlaps a stronger traceability proposition. The research must allow an integration to eliminate work Gibson would otherwise build.

## What the repository establishes

At Gibson main `babef4b3ce969289b698c55babffd97c2f5720b7`, planner/decomposer playbooks provide useful templates and procedures. Decomposition lint and DAG checks are executable and passed the inspected four-issue fixture. They do not prove a specification is complete or useful. No dedicated brief-to-spec executable or independently demonstrated nontechnical intake path was identified in this audit.

Claims, worktrees, bounded execution, gates, test integrity, local proof and exact-head review evaluation are substantial reusable assets. They still depend on actual runtimes and reviewer/deployment connections. The criterion-marker helper provides closure hygiene; a criterion appearing in a PR body is not evidence that a user can perform it. The portable receipt collector explicitly remains unavailable in the inspected slice; report-only schemas do not establish deployed behavior.

These observations support connecting existing assets with small explicit contracts and a real vertical demonstration. They do not justify replacing the harness wholesale or declaring its complete end-to-end promise already delivered.

## Integrated product decision

Recommend one operator journey with explicit component boundaries before a repository merger. Agent Kontrol already owns tasks, fleet state, decisions, progress and runtime presentation; Gibson owns portable repository contracts and evidence checks. A web application can make “describe -> understand -> choose increment -> see proof -> decide -> release” feel like one product while artifacts remain exportable and repository gates retain authority.

Use shared identifiers and versioned references across the boundary, not two competing status truth stores. Agent Kontrol can project the product/spec/increment/run/evidence chain and request effects. The repository adapter validates the allowed transition and records actual observations. The UI cannot manufacture approval from a green badge or override a denied repo gate. Keep GitHub source/checks and the actual deployment authoritative for their own facts.

Defer a literal monorepo or unified deployment until repeated changes show that cross-repository contract/release overhead exceeds the benefits of portability and independent operations. A merged tree does not itself provide durable event delivery, atomic admission, or a working reviewer connection.

## Make, integrate, defer

Own the plain-language product contract, explicit unknowns/decisions, useful-slice decomposition, outcome/evidence linkage and the owner's explanation of ready/blocked/disproved state. Reuse the current kernel/adapter direction rather than introduce another authority layer.

Benchmark Spec Kit/Kiro-style artifacts against the current playbooks before inventing a specification language. Keep execution with existing coding agents or an OpenHands-style adapter. Use GitHub/CI/deployment evidence and existing attestations where applicable. Langfuse is an optional trace/evaluation/prompt-experiment adapter; an evaluation score is not release permission. Atomic deserves a disposable compatibility experiment: distinguish its native sandbox from its Git shim, preserve source/review identity, and measure cost/recovery. Do not replace physical worktree isolation or source authority from a product page.

Defer a generic graph database, new scheduler, mandatory multi-model consensus, new UI workbench, broad reducer platform and self-hosted observability cluster until a selected useful slice needs them and a comparison supports their cost.

## Value-ordered increments

1. **Description to accepted spec.** A short intake plus readable versioned artifact exposes assumptions, decisions, non-goals, requirement IDs and observable scenarios. Benefit: the owner can understand and correct the intended product before code. Negative cases include contradictory requirements, omitted data boundaries and invented business rules. Start with existing chat and planner artifacts.
2. **Spec to dry-run release scope.** Map each requirement to a useful increment or explicit deferral, a bounded issue contract, dependencies, acceptance scenarios and verification. Reuse lint/DAG tools. Benefit: see the first useful delivery and its true prerequisites before opening work. Reject cycles, missing scenario coverage and infrastructure-only “increments.” Publication remains a separate authorized action.
3. **One increment to verified running behavior.** Drive one existing execution/review/preview/release path and retain exact source, test, reviewer and deployment bindings. Benefit: receive a working capability and inspect its proof. Missing live evidence remains unknown; a changed head or deployment cannot reuse stale proof. Complete applicable readiness before calling the result production-ready.
4. **One operator experience.** Project the same artifacts and decisions into existing Agent Kontrol surfaces, with resumable handoffs and truthful current state. Benefit: less context switching and fewer owner interventions. Evaluate confusion, contradictory state, replay/recovery and time to the appropriate action before consolidating codebases.
5. **Measured design improvement.** Compare repeated user outcomes, defects, rework, waits and total effort; propose a scoped change to design guidance, architecture, prompts or the existing mechanism. Ship and replay the improvement through normal review. Benefit: the next comparable delivery is better. Remove redundant complexity through existing authority boundaries rather than only adding checks.

Enterprise assurance is embedded from the first spec and completed as applicable before the relevant release; it is not a final generic hardening sprint that retroactively makes earlier claims true.

## First demonstrator and evaluation

Use a clearly fictional reference “service request tracker” to demonstrate the artifact chain: a requester submits a request, a coordinator triages it, and the requester sees its status. Include two roles, a forbidden cross-user read, failure recovery and a changed requirement. This is a documentation/example fixture, not evidence of customer demand or an implemented application. Select one already prioritized real adopter journey separately before a delivery trial.

Compare current Gibson playbooks, a minimal specification toolkit baseline, and a proposed thin artifact spine at matched effort and access. Include ambiguous briefs, conflicting requirements, a legacy repo with already-shipped work, a changed requirement, and a privacy/security-sensitive constraint. Publish example cases; reserve an independently curated held-out subset for the later trial. No held-out dataset or comparative result is claimed to exist yet.

Measure invented material requirements, missed constraints, owner corrections/minutes, time to an accepted spec, requirement/scenario coverage, time to a useful verified release, actual task success, escaped defects, repair rounds, no-verdict attempts and observed cost. Separate waiting, reviewer execution, owner holds and infrastructure/tool failures. A before/after anecdote or model consensus is directional evidence, not a causal productivity claim.

Fail the demonstration if a material requirement disappears, an unaccepted assumption becomes scope, a prose checkmark substitutes for executable evidence, a stale source/deployment is called verified, an unknown gate becomes passed, or the intended user cannot complete the task. Reject permanent complexity when it adds no justified outcome/quality improvement over the declared trial window.

## Enterprise assurance profile

Declare applicability, required evidence and observed status for functional correctness, identity/authorization and tenant boundaries, data/privacy/retention, security/supply chain, reliability/recovery, operations/SLOs, deployment/migration/rollback, auditability, and accessibility/usability. Separate tested behavior from source/config claims and third-party assurances. A plan cannot confer SOC 2, ISO certification, legal compliance or a security guarantee.

## Decisions and reversal evidence

The consequential owner decisions are the first user/market wedge, the first real adopter journey, what enterprise assurance applies to it, whether one product experience is desired, and which existing integration is worth an actual trial. Technical implementation choices within the accepted scope should remain with the engineering/review process.

My non-obvious alternative is a small GitHub-native reference workflow using existing specification tools and an optional Agent Kontrol presentation, rather than a new all-in-one platform. Reverse that preference if representative users demonstrably need a persistent workbench, integration handoffs dominate total delivery cost, or a thin adapter approach cannot preserve trustworthy recovery/evidence at acceptable effort. Evaluate Atomic as a possible substitute for some traceability work rather than assuming Gibson must own every layer.
