> **Authority:** Non-normative research. This is advisory material and supplies no release approval or operational authority.

# Independent product-design research

Please help test this owner-authored hypothesis: a vendor-neutral software toolkit/reference architecture can turn a human-readable product description into a product specification, bounded scope of work, useful increments, and a verified release of reliable enterprise software.

Evaluate a possible product made from:
- A portable Git/GitHub-oriented toolkit with Markdown planning playbooks, issue/scope/dependency validation, isolated coding workspaces, automated checks and review evidence, and release-evidence artifacts.
- A web control plane with project/task coordination, human decisions, progress views, and telemetry.
These are generic capability descriptions, not a live-system inventory. Do not infer their maturity, successful deployment, private architecture or operating state.

The intended primary user is a nontechnical owner working with one primary coding model. Multiple-model research or review can be optional; do not make this five-model panel a runtime requirement. Enterprise readiness must be an explicit applicable profile and evidence, not a blanket promise or certification.

Public ecosystem sources to consider (you cannot browse in this call; cite these as supplied source descriptions, not as pages you opened):
1. Atomic.dev describes semantic change/provenance and intent/criterion/task/evidence/review relationships: https://atomic.dev/features/ and https://docs.atomic.dev/getting-started/atomic-vault
2. Its Git shim documents linked-Git-worktree limitations, while its native project also describes COW sandboxes; assess those separately: https://docs.atomic.dev/getting-started/git-shim and https://github.com/atomicdotdev/atomic
3. Langfuse provides tracing, prompt versions, datasets/experiments/evaluation, feedback and annotation: https://langfuse.com/docs . Deployment/privacy/licensing choices require assessment: https://langfuse.com/self-hosting and https://langfuse.com/docs/observability/features/masking
4. Existing spec-driven approaches: https://github.github.com/spec-kit/ and https://kiro.dev/docs/specs/
5. Execution/durable-workflow alternatives: https://docs.openhands.dev/overview/introduction and https://docs.temporal.io/ai
6. Build provenance: https://docs.github.com/en/actions/concepts/security/artifact-attestations

Produce an independent research memo, 1200-1800 words if budget permits:
A. Critique the product hypothesis, target user, differentiation, alternatives and strongest falsification cases.
B. Compare separate products vs one integrated experience/shared contracts vs one repository/deployment for toolkit + control plane. Recommend reversible stages and what must remain portable.
C. Define the human-readable artifact chain: description, accepted spec, scoped increments, acceptance scenarios, implementation, independent evidence and released outcome. Include versioning, changed requirements, unknowns and authority boundaries.
D. Propose 4-6 value-ordered increments with concrete user benefit, minimum deliverable, acceptance/negative cases, real dependencies and what remains unproven. Demonstrate useful benefit before broad infrastructure.
E. Propose one first demonstrator, matched baseline/held-out evaluation, enterprise-readiness dimensions, measures for user value/design quality/delivery speed/reliability/total cost, and when to simplify or reject the design.
F. List five consequential decisions and one non-obvious alternative worth testing.

You are advising product research only. No repository code, private files, credentials, live operations, customer data, recovery state, work histories, system configuration or performance measurements are included. No browsing/tool/implementation authority is granted. Do not claim to have inspected software, fabricate research results or quote vendor benchmarks as reproduced.
