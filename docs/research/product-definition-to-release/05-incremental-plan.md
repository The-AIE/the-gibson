# Incremental product plan for Goal 1

## Product outcome and sequencing rule

A human-readable product definition becomes a faithful specification, useful bounded work and a demonstrably released capability. Each increment should improve a user's decision or result before the next infrastructure layer is built.

This is proposed scope, not implementation dispatch. Before turning a row into work, refresh existing implementation/issues/claims, resolve consequential decisions, and use the current admission/review path. The research creates no duplicate epics and grants no live integration or release permission.

## First experiment over the existing stack

The ladder below describes benefits, not five greenfield subsystems. The source-informed model follow-ups retract their earlier proposals to rebuild existing planning, workspace and gate machinery. The first candidate implementation is one honest acceptance/evidence packet using an existing plan, issue and check path.

| Step | Bounded work and reuse | Demonstrable exit |
|---|---|---|
| P1: Existing-artifact packet | Import one accepted plan version and scoped increment; reference current gate/review/receipt outputs; render Markdown or a static report first | An owner can explain what was promised, what is linked, what behavior has evidence, and what remains unknown |
| P2: One behavioral bridge | Connect one criterion to one meaningful scenario, exact source/environment and retained result; add only the missing schema/adapter | A marker-present but missing/failed scenario stays "not demonstrated"; old-source results stay stale; independent review remains separate |
| P3: One changed requirement | Preserve the prior accepted version; identify only affected scope/scenarios/evidence | The changed promise cannot inherit obsolete evidence, and an unaffected result is not needlessly invalidated |
| P4: Real release demonstration | Continue the same useful increment through applicable review, authorized deployment and observed user flow | Source, artifact/deployment, user behavior and required authority are evidenced; an unknown deployment is never called released |

P1 can use existing records without a new service. If the packet fails to improve an owner's decision, revise or stop the integration bet before building a workbench. P2's proposed behavior is an implementation acceptance target, not a new gate enacted by this document. P4 is still necessary for the full product claim; stopping at P2 demonstrates only the smaller evidence slice.

Project the same references into Agent Kontrol only when that comparison is useful; do not create another manager, copy its transactional state into Git, or wait for a repository merger. Compare the packet with current artifacts and an evidence/change layer over existing spec tools. Refresh current ownership before selecting the concrete target.

## Increment 1 — Description to accepted specification

**Owner benefit:** understand, correct and accept the intended product before implementation.

**Minimum deliverable:** a short plain-language intake using existing chat/planner patterns, a versioned product definition/specification, stable requirement IDs, explicit assumptions/unknowns/non-goals, user scenarios and a plain-language change summary. Produce an exportable artifact, not a mandatory hosted account.

**Reuse:** planner and operator decision templates, #18's single-primary-model path, existing research/refinement contracts where applicable. Following the later owner question, [trial OpenSpec's released artifact workflow](10-openspec.md) as the first candidate, preserving current PLAN/issue outputs; compare with a minimal Spec Kit-style path before building another specification framework. Following the panel, also compare a narrow acceptance/evidence-and-change compiler over existing agents/spec tools with the full guided product path.

**Scope:** preserve meaning; clarify consequential ambiguity; distinguish requested requirement from model suggestion; record the appropriate acceptance/decision reference. Low-risk assumptions may remain visible without manufacturing a new confirmation step for every edit.

**Acceptance:** an independent evaluator can trace each material requirement to the original request or an accepted decision; the intended owner can explain what is in/out; an ambiguous brief exposes questions; contradictory constraints stay unresolved; requirements and assurance applicability are versioned.

**Negative cases:** invented payment/data/residency rules; a suggestion silently treated as accepted; omitted constraints; an unanswerable question becoming a guessed business fact; an unaccepted material change presented as approved.

**Dependencies:** one bounded user/problem and accessible current product context. No general reducer engine, dashboard, telemetry service or new VCS is required.

**Still unproven:** better user understanding and less downstream rework at matched effort.

## Increment 2 — Accepted spec to useful dry-run scope

**Owner benefit:** see the first useful result, true prerequisites, deferrals and how each result will be accepted.

**Minimum deliverable:** a scope-of-work package with one or a few independently useful increments; requirement/scenario mapping; dependencies; affected surfaces; existing-work reconciliation; risk/verification/rollout notes; and proposed issue changes. Default to a dry run.

**Reuse:** decomposer playbook, decomposition lint/DAG tools and existing #167 research packet seams. Refresh those components rather than assuming every child is missing or forcing their entire platform to precede a useful pilot.

**Acceptance:** every accepted requirement is covered or explicitly deferred; each increment has a user/operator benefit and demonstrable exit; dependencies form a valid order; already-shipped work is not rebuilt; implementation-changing questions are separated from independently executable work; proposed GitHub effects are reviewable before authorized publication.

**Negative cases:** an infrastructure-only wave called a user increment; a requirement disappearing; a cycle or overlap; stale issue wording overriding current implementation; a large task split only to improve issue/PR counts.

**Dependencies:** Increment 1's accepted version and current target-repository evidence. The validator proves structure, not semantic completeness; preserve independent judgment.

**Still unproven:** that the resulting scope reaches useful value earlier than the current planning baseline.

## Increment 3 — One scoped capability to verified release

**Owner benefit:** receive one running useful capability and inspect what proves it.

**Minimum deliverable:** use an existing target repo/runtime/deployment route for one admitted increment. Link definition/spec/scenario to issue, exact source, real checks, independent review/evaluation, authorized deployment and post-release observation. Keep the portable receipt's unsupported fields unknown.

**Reuse:** current claim/worktree, gate/test integrity, local proof, review-evidence, preview/UX/security and release tooling; existing source/build attestations where applicable.

**Acceptance:** positive, forbidden and recovery scenarios run against the relevant source/deployment; exact-head review is eligible and current; applicable checks/authority are present; a deployment/artifact identity binds to the source; an intended user completes the flow; rollback/recovery and cleanup evidence are reported truthfully.

**Negative cases:** criterion text alone as proof; stale head/deployment; missing reviewer silently skipped; unknown gate called passed; source merger called deployed; smoke success used to claim all business behavior; preview-only evidence marketed as production readiness.

**Dependencies:** functioning actual runtime/reviewer/deployment connections, a selected real capability, required product decisions and all applicable assurance before its release. A working end-to-end path is a prerequisite; a full control-plane rewrite is not.

**Still unproven:** repeatability across products and enterprise profiles.

## Increment 4 — One integrated operator journey

**Owner benefit:** understand and act on the same product/spec/increment/evidence state without reconciling multiple tools.

**Minimum deliverable:** project the portable artifacts and decisions into existing Agent Kontrol surfaces. Show the current meaningful stage, accepted version, next useful result, evidence/limitations, blocked reason and bounded owner action. Preserve export/standalone use and authority.

**Reuse:** Agent Kontrol's existing task/decision/progress, APIs and component boundaries. Add the smallest shared contracts and read model necessary for the tested journey.

**Acceptance:** owner task success/comprehension improves against the existing path; state remains consistent after retry/restart/head change; unavailable observations remain unknown; a UI cannot override repository gates; a decision refers to the correct scope/version; fallback to portable artifacts works.

**Negative cases:** competing writable status truth; a badge expands permission; duplicate tasks/effects after retry; context switching merely moves into another dashboard; toolkit use now requires the hosted service.

**Dependencies:** evidence contracts from preceding increments, the existing product surfaces and a bounded integration slice. Review stream/inbox work is relevant where that actual journey needs it; the whole reducer catalogue is not automatically on the critical path.

**Still unproven:** whether a single product offering, monorepo or coupled deployment is worthwhile.

## Increment 5 — Measured design and delivery improvement

**Owner benefit:** later comparable delivery improves in usefulness, reliability, speed or total effort.

**Minimum deliverable:** a report linking observed outcomes to a falsifiable improvement proposal, one bounded comparative change, independent evaluation, normal delivery and repeat-use observation. Start with existing local/versioned records; optional observation adapters may assist.

**Reuse:** #210's failure-to-protection/replay, #214's advisory-first propagation, existing lessons/decisions and an optional Langfuse/OTel adapter. Keep current memory claims and public/private boundaries.

**Acceptance:** design/requirements problems, implementation defects, missing/no-verdict execution and explicit holds are distinguished; actual queue/runtime/release intervals are separated; changes preserve quality and reduce a demonstrated cost or failure; ineffective complexity is narrowed or retired through existing authority.

**Negative cases:** model agreement called measured improvement; synthetic tests substituted for user success; unknown cost reported zero; more controls automatically declared learning; elapsed time attributed to hardware or scheduling without measurements.

**Dependencies:** enough comparable observed deliveries and a specific learning question. Do not wait for universal telemetry or require every model on every task.

## Enterprise readiness is a profile across all increments

Capture the relevant requirements at Increment 1, include their work/evidence in Increment 2, satisfy the release's applicable floor before Increment 3, expose their real status at Increment 4, and measure regressions at Increment 5. Higher assurance may expand scope; it must not be hidden in “done.”

## Now / Next / Later

The [release and epic map](11-release-structure.md) distinguishes lasting outcomes from shippable checkpoints. The increments above describe benefits, not an instruction to open five simultaneous implementation lanes.

**Now:** complete this research package and choose the first user segment, real pilot journey, assurance profile and representative evaluation. Keep existing recovery priorities and claims intact. Candidate prototype work is not automatically admitted.

**Next:** try P1 over existing records, then admit only the missing P2/P3 connection before completing P4. Exercise the description/spec/scope chain with current artifacts rather than rebuilding it. Refresh and reuse the existing #18/#165/#167/#210/#214 contracts; create only bounded missing work after reconciliation.

**Later, if earned:** the integrated operator experience, broader architecture profiles, ecosystem adapters and cross-product learning. Consider repository/deployment consolidation only after integration costs and user benefit are measured.

Estimates should be derived from the selected scope/runtime and a bounded trial. This research does not invent calendar commitments or claim a finished implementation backlog.
