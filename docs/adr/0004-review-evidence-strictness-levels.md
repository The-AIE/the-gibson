# ADR-0004 · 2026-10-23 · An adopter starts lenient and each repository chooses its review-evidence rung

**Status:** Proposed. Nothing here is built. The evaluator, the trust file, the workflow and the template are unchanged by this PR.
**Owner decision required:** this record proposes that the shipped default be *less* strict than this repository's own gate. AGENTS.md's ratchet says a gate may only loosen with the owner's sign-off, and D-014 says the owner is out of the review loop, so the record also asks how those two rules apply to a repository lowering its own level (Open questions, Q3). Mark decides; this record is the question, not the answer.
**Decision record:** `memory/DECISIONS.md` D-021 points here.
**Related:** D-006 (adoption is a ladder), D-011 / D-012 / D-015 (review-independence levels E0..E4 and the Tier C floor), D-013 / D-014 (one attestation model; owner out of the loop), D-019 (`ownerCountersignVendors`, the first per-repository policy knob in the trust file, the-gibson#534), ADR-0001 (the-gibson#511).

## Context

The `review-evidence` merge gate has two halves. The **evaluator** (`scripts/pr-review-evidence.mjs`, driven by `.github/workflows/pr-review-evidence.yml` and configured by `config/review-evidence.v1.json`) is portable: it reads only GitHub's API and a committed JSON file, never runs pull-request code, and every one of its decisions is a closed reason token that fails closed. The **producers** of evidence are not portable. Every receipt the evaluator accepts today comes from a GitHub App identity the operator created and installed (lane-bot author Apps, a reviewer-only independent-review App, a vendor connector App), posted by a controller that runs on the operator's own hardware from a private repository, or from the owner's countersign of a hand-run review.

The open source readiness assessment of 2026-10-23 measured what that costs a stranger: an adopter following `playbooks/adopt.md` reaches green `claim-isolation` and `sensors` in about an hour, then stalls for one to two days on **reviewer identity**: creating a GitHub App, installing it, storing its key, writing an identity into the trust file, and standing up something that posts under it. Until then every head is `pending: no-receipt-at-head` and nothing can merge. `docs/13-adoption.md` § "Dedicated reviewer identity (G14 setup, once per org)" documents the stall as a step; it does not remove it.

Mark's direction the same day: *the default could be less strict, and then the user can choose for each project.*

Three facts shape the design:

1. **D-006 already made adoption a ladder** (enforcement before orchestration), but the ladder has one review rung, and it is the operator's own. There is no rung below "signed App identities" and no rung above it that names what delivery control adds.
2. **D-019 introduced the first per-repository policy knob**, `ownerCountersignVendors`, as explicit configuration rather than a constant in code, with the validator refusing dead or misspelled entries. This record generalises that move: policy that differs between repositories lives in committed, validated configuration, never in code and never in a per-push input.
3. **The target repositories already sit at different rungs in practice.** This repository requires `review-evidence` with a closed identity table (D-013/D-014/D-019). The largest target, TargetApp in the ledger's naming, requires `review-evidence` plus `DCO`, `quality` and `build-e2e-required`, runs a sibling evaluator with per-provider capabilities (`routine`, `schema`, `tier-c-delegated`), protects a `release` branch under delivery control (docs/23) and carries migration-safety and post-merge verification. ProductApp requires `gate`, `security-fast`, `authz-matrix`, `posture` and `zap-baseline` and does not require `review-evidence` at all. The difference is real and unrecorded; this record gives it names.

## Decision (proposed)

Add a `reviewPolicy` key to the per-repository delivery configuration, carrying an integer **level** 0..3. The proposed canonical path is `.agents/gibson-delivery.json`, which the `gibson-ship` preflight reads today; `scripts/delivery-control/` and `scripts/git-configure.sh` read a root `.gibson-delivery.json` today and no adopter has either file, so the path is Q9 and the migration below is where the two converge. The evaluator reads the level from the **default branch's committed copy** through the trusted checkout `pr-review-evidence.yml` already performs, and selects which evidence sources count at that level. The adoption flow asks the adopter to choose a level with the Ask Contract and writes `1` unless they choose otherwise.

```json
{
  "repo": "OWNER/REPO",
  "defaultBranch": "main",
  "requiredContexts": ["quality", "review-evidence"],
  "reviewPolicy": {
    "level": 1,
    "reviewerVendor": "codex",
    "decidedBy": { "login": "OWNER", "date": "2026-10-23" }
  }
}
```

The reference reviewer workflow's path is **fixed**, `.github/workflows/gibson-review.yml`, and not configurable: a configurable path would let a committed policy point level 1 at any other workflow able to post the marker, which changes what a level-1 pass means. `reviewerVendor` is the one vendor the reference workflow may call at this level; it is validated against the trust file's `attestationVendors` and is what the evaluator uses for same-vendor exclusion (the receipt's own `reviewer-vendor` field must match it, or the receipt is refused).

Everything under "Decision (proposed)" is a proposal. Where a sentence describes what the evaluator, the workflow or a script does **today**, it says "today"; everything else is what the Tier C implementation PR would add after Mark decides.

### The four levels

| Level | Name | Who it is for | What clears a head | What is new in the tree |
|---|---|---|---|---|
| **0** | solo | One maintainer, no second model available or wanted | Nothing. `review-evidence` is **published** on every head but is **not a required context**; branch protection does not list it. | The workflow and a minimal trust file (owner as author, `github-actions[bot]` as reviewer). |
| **1** | second-opinion (**shipped default**) | A maintainer or small team that writes with one model and wants another to read every head | A `workflow-review:v1` receipt posted by the repository's **reference reviewer workflow** under the `github-actions` App identity (slug `github-actions`, id 15368), naming a `reviewer-vendor` different from every author vendor the head declares (the workflow refuses to review a head whose declared author vendor is its own; Q6 offers the alternative). Stronger sources also count when present (a listed App identity's receipt, an owner countersign), under the same cross-vendor rule; **none is required, and no adopter-created App.** Control-plane heads need one of those stronger sources (below). | The reference workflow plus one repository secret (a model API key for a vendor other than the one the adopter writes with); for a public repository, an Actions event policy allowing `pull_request_target` (below). |
| **2** | signed identities | A fleet of agents under distinct vendors (this repository today) | Today's rules unchanged: a formal review at the exact head by a listed Bot login (user type `Bot`, login in the **closed** trust table), or a `review-evidence:v1` comment bound to a listed GitHub App by slug and id; lane-bot author identities or owner-identity commits with an `Agent-Vendor:` trailer; same-vendor exclusion; `independent` clears unvendored owner commits; `ownerCountersignVendors` (D-019); unresolved author → failure. | At least one App identity the adopter controls or trusts, with its install and key. |
| **3** | delivery control | A repository whose merge ships to production (TargetApp today) | Level 2 **plus**: `scripts/delivery-control/audit.sh` passes; the Tier C human gates of docs/14 are stops; a `Migration safety` block is required when schema paths change; post-merge verification against the deployed SHA (docs/30; ADR-0003's hypothesis when it is tested); schema merges serialised. Whether carve-out paths additionally need a reviewer-only identity is **provisional** (Q8). | Delivery-control configuration (model, production branch, environment) and the verification wiring. |

Levels are **cumulative in guarantees, not in accepted sources**: every guarantee at level *n* holds at level *n+1*, while the set of receipts that count narrows (level 2 refuses the level-1 workflow receipt because its author-vendor side rests on self-declaration). Promotion is a one-key change plus whatever the new rung needs installed; the status description on every head names the level in force ("level 1: pass: github-actions[bot] (anthropic)"), so a reader of any PR knows which rung cleared it.

### What does not loosen at any level

Stated so it cannot be read out of the table above.

- **Fail closed, everywhere the evaluator already does.** `head-moved`, `ambiguous-head`, `api-error` (including a truncated commit list), `config-error` (missing, unreadable, invalid or unknown-key trust file), an unlisted or unverified author at level 2 and above. None of these gains a lenient branch at a lower level.
- **Receipts bind to the exact head.** A receipt at another head is `stale-head-only`; one that predates a base retarget is `stale-base`; a receipt at the wrong head is never evidence at any level.
- **Tampering voids.** An edited machine receipt is a tombstone (`editedAtAll`), an owner-countersigned comment edited by anyone else is a tombstone (`editedByOther`), a comment deleted at or after the newest pass voids that pass (`evidence-deleted`), newest-wins with `fail` dominating on a same-second tie. Level 1 receipts inherit all of this unchanged because they are App-authored comments like every other receipt.
- **The `review-evidence` status is always published at every adopted level.** Level 0 removes it from `requiredContexts`; it never removes the workflow or silences the status. (A repository that has not installed the evaluator publishes nothing; the migration table calls that state *undeclared*, below level 0.) A level-0 repository that later wants level 1 adds one context to branch protection and has history to look back on.
- **The level is read only from the repository's committed default-branch configuration.** The workflow runs on `pull_request_target` and checks out the default branch, never PR code, so a pull request's own copy of `.agents/gibson-delivery.json` is never what the evaluator reads. This mirrors the repo-owned rule of the local pre-push gate's `.fleet-gate`: a gate file counts only as the bytes on the default branch; a copy that is new, edited or deleted in a lane is a gate *change*, and a lane cannot make its own change effective for itself. A pull request that edits `reviewPolicy` is evaluated under the level in force; its diff touches `.agents/`, which `carveOutPath()` names in the status description today as a control-plane path (description only, no verdict change since D-014); the new level applies to heads evaluated after it merges, **including pull requests already open**, which is why the lowering PR itself carries the stronger gate below.
- **Lowering a level is a loosening under the ratchet.** AGENTS.md: "The ratchet may tighten autonomously; it may only loosen with the owner's sign-off." That it is required is not in question; how it is expressed after D-014 is Q3. The proposed machine-checkable form: `reviewPolicy.decidedBy` names the owner login from the trust file and a date, the validator refuses a level below 2 without it, and a head that changes `reviewPolicy.level` downward or touches the reference workflow's fixed path is **not clearable by a `workflow-review:v1` receipt**; it needs an `owner-attested-review:v1` countersign (the owner's word at the exact head, which exists today) or a listed App identity's receipt. Its limit, stated: a file can name the owner without the owner having merged it; the check that the owner actually did is the post-merge `merged_by` probe D-019 already lists as a follow-up.
- **The adoption PR does not bootstrap itself through the new level.** The PR that installs the reference workflow and the configuration is evaluated, if at all, under the absent-key rule (level 2) and has no level-1 receipt available, so it is merged under the repository's protection **as it stands before adoption**, which does not yet require `review-evidence`; `scripts/git-configure.sh --apply` adds the context to branch protection only after that merge. Level 1 therefore never clears its own installation. The same ordering holds for a repository raising its level.
- **The hard blocks on actions** in the fleet's operating card (secrets and keys, billing, legal pages, destructive operations, unrequested pushes) are untouched, exactly as D-014 and D-015 left them. Levels govern what counts as review evidence, not what an agent may do.

### Why a level-1 receipt from `github-actions[bot]` is acceptable evidence

The level-1 receipt is a comment posted with a workflow's own `GITHUB_TOKEN`. GitHub stamps such a comment with `performed_via_github_app` = `{ slug: "github-actions", id: 15368 }`, which the evaluator checks today for every App receipt, so the trust table would list `github-actions[bot]` like any other App comment identity, bound by slug **and** id. (Checked while drafting this record, on existing `GITHUB_TOKEN` comments in this repository and in TargetApp: every one carries `performed_via_github_app` slug `github-actions`, id 15368, user type `Bot`.) The reference reviewer workflow is a **separate workflow file** from `pr-review-evidence.yml`, at the fixed path `.github/workflows/gibson-review.yml`: the evaluator workflow keeps `issues: read` and `pull-requests: read` and never posts comments; the reviewer workflow has `contents: read` and `pull-requests: write` (creating an issue comment on a pull request needs a write scope) and nothing else, runs on `pull_request_target` (`opened`, `reopened`, `synchronize`, `ready_for_review`), and sets its job name to `review <pr-number> <head-sha>` from the event payload.

**Prerequisite the adopter must act on.** GitHub now ships a default Actions event policy that blocks `pull_request_target` in **public** repositories that have no explicit event policy of their own; it is in evaluate mode today and GitHub enforces it on 2026-12-02 (GitHub Docs, "Securely using pull_request_target", read while drafting this record). Private and internal repositories are unaffected. **For a public repository, level 1 is available only once an Actions event policy explicitly allows `pull_request_target`** (an owner action; the adoption flow asks for it with the Ask Contract and `git-configure.sh --audit` reports its absence as drift). A **fallback trigger** is designed but **not available**: an hourly `schedule` that lists open pull requests and reviews each in a matrix job named `review <pr-number> <head-sha>`. It reads no PR code either, but a scheduled run has no `pull_requests[]`, so it depends entirely on the job-name binding below, which is unverified; until the spike settles it, the fallback is not part of the security argument and a public adopter has exactly one level-1 path. This repository's own `pr-review-evidence.yml` is public and uses `pull_request_target` too; it is subject to the same policy and needs the same owner action before 2026-12-02 (Q11, Follow-ups).

What makes the receipt trustworthy is the chain behind the stamp:

1. **The workflow file that runs is the default branch's.** `pull_request_target` reads the workflow from the base repository's default branch, never from the PR. A pull request cannot change which reviewer runs, what prompt it uses, which model it calls, or what it posts. This is the trust boundary `pr-review-evidence.yml` relies on today; the reference reviewer workflow would carry the same trigger comment and the same `gibson:approved-pr-target` marker.
2. **The reviewer job never executes PR code.** It checks out the default branch, fetches the PR diff and metadata through the API, sends the diff to the model as data, and posts the result. The code under review has no path to the job's token or secrets. A workflow that checked out and built the PR head under `pull_request_target` would hand the author the token; the reference workflow is written so it cannot be edited into that shape without a diff on the default branch.
3. **The receipt inherits every App-receipt check.** Exact-head binding, edit tombstones, deletion voiding, retarget staleness and newest-wins apply because `collectEvidence` would file it as a comment from a listed App; the new code is the marker and the run binding, not the tamper rules.
4. **The receipt carries a `run-id`, and the evaluator binds it to this head.** The `github-actions` identity is shared by *every* workflow in the repository, so the identity alone proves nothing. The evaluator fetches the run and its jobs and accepts the receipt only when: the run belongs to this repository; `path` equals the fixed `.github/workflows/gibson-review.yml`; `event` is `pull_request_target` or `schedule`; `status` is `completed` and `conclusion` is `success` at evaluation time; `created_at` precedes the comment's `created_at` (the comment is posted *during* the run, so no completion-before-comment relation is asserted); for a `pull_request_target` run, `head_sha` equals this head and `pull_requests[]` names this PR; and a job of that run is named `review <this PR number> <this head sha>`. The first two bindings are checked today on this repository's own `pull_request_target` runs (the run object carries `path`, `event`, `status`, `conclusion`, `created_at`, `head_sha` equal to the PR head, and `pull_requests[]` with the PR number and head), so the `pull_request_target` path is verifiable with documented fields alone. The job-name binding is **unverified**: it rests on the job's `name` being set by the default-branch workflow file from the event payload or the scheduled listing, which a PR cannot forge, and the implementation spike must show that such a name appears in `GET .../runs/{id}/jobs`. There is a reason to doubt it: a matrix job in TargetApp's CI appears in that endpoint with its `${{ matrix.shard }}` expression unexpanded, so a job name may not carry evaluated payload values at all, and the spike may have to find another run-side field the default-branch file controls. Until it does, the scheduled fallback trigger (which has no `pull_requests[]`) is **not available**, and a public adopter's only level-1 path is the Actions event policy allowance. A comment with no run id, an unknown run id, a run of any other workflow file, or a run that does not bind to this head is not evidence.
5. **The reviewer's vendor is committed configuration, not a claim in the comment.** `reviewPolicy.reviewerVendor` on the default branch names the one vendor the reference workflow may call; the workflow reads it from the trusted checkout and selects the matching endpoint and secret from its own fixed file (one named secret per vendor, `GIBSON_REVIEWER_KEY_<VENDOR>`). The evaluator applies the same-vendor exclusion between `reviewerVendor` and the author vendors it resolved for the head, and refuses a receipt whose `reviewer-vendor` field differs from it. The residual, stated: the evaluator proves which vendor the committed policy *authorised*, and that the receipt agrees; it cannot prove which endpoint a run actually called, so a reviewer workflow edited to call another vendor is caught only as a control-plane change (next section), not by the receipt. The workflow itself declines to review a head whose declared author vendor equals `reviewerVendor`, leaving the head `pending` with a description that says so.

**What a write-access author, or a fork author, can still do at level 1**, stated plainly so the rung is chosen with eyes open:

- **Prompt-inject the reviewer.** The diff is attacker-controlled text and the model reads it. The workflow never executes it, but a diff that carries instructions to the reviewer can steer a model toward `pass`. This is a property of every model reviewer at every level, including level 2's lane-bot reviewers and the fleet's own; the reference workflow wraps the diff as quoted data under a fixed prompt and the fleet severity contract, and AGENTS.md's G16 (evidence of prompt-injection steering an agent) is the stop. It is not a reason to prefer level 2 over level 1; it is a reason that any level below E4 is a claim and the merging party still reads the diff (D-011, D-015).
- **Post a forged receipt from another workflow.** Any workflow in the repository with `pull-requests: write` or `issues: write` runs under the same `github-actions[bot]`, and a `pull_request`-triggered workflow runs the PR's copy of its file. Without the run binding this would be a one-line attack; with it, the forged comment's run id belongs to a different workflow path, or to a run whose jobs name no such head, and the receipt is refused.
- **Replace the reviewer.** A PR that edits the reference workflow is reviewed by the *current* copy, which would then be replaced by whatever the PR says. The current copy is a model, so this is a real path, and level 1 does not leave it to the model: a head touching `.github/workflows/**` (the reference workflow's fixed path included) or `.agents/gibson-delivery.json` is **not clearable by a `workflow-review:v1` receipt**. It needs an `owner-attested-review:v1` countersign or a listed App identity's receipt, as the ratchet bullet above says. The residual is the owner's own word, as it is today for every countersign.
- **Lie about the author's vendor.** At level 1 the `Agent-Vendor:` trailer is self-declared, unlisted authors resolve to vendor `human`, and there are no lane-bot identities to check against. An author who writes with the vendor the reviewer calls, and omits or falsifies the trailer, obtains a same-vendor second opinion (E2 in D-012's taxonomy, not E3). Level 1 accepts this; it is exactly what level 2's closed identity table and lane-bot Apps close. The receipt records which vendor reviewed, so the gap is visible after the fact, never silent.
- **Cancel or break the run.** Produces no receipt and leaves the head `pending`; it cannot produce a pass.
- **Write to the default branch directly, or bypass branch protection.** An actor who can push to the default branch, or merge past protection, can replace `gibson-review.yml`, change its prompt, vendor or model, and have the next run post a well-formed receipt under the shared identity. The same actor can edit the trust file at level 2, edit the evaluator workflow at every level, or remove `review-evidence` from protection, so this actor is the repository's **trust root and is outside the evaluator's threat model at every level**, not a level-1 exposure. The controls the harness applies and audits operate *inside* that boundary, not against it: `git-configure.sh --apply` writes default-branch protection with `enforce_admins: true` and no bypass allowances, so that while those settings stand, workflow changes reach the default branch only through a pull request, and `--audit` reports drift from that state so a change to the settings is noticed. They constrain drift; they cannot stop an actor who can alter the protection or the rules themselves. No evaluator can authenticate a workflow revision against an actor who owns the branch the evaluator trusts; the record says so rather than promising it.

What a write-access author **cannot** do at level 1: edit a receipt into a pass (tombstone), delete a fail to resurrect an older pass (timeline voiding), move a pass from one head to another (exact-head binding, job-name binding), make the reviewer run their code (no checkout of PR code), pick the reviewer's model and prompt from the PR (default-branch workflow file), or swap the reviewer and have the swap cleared by the reviewer being swapped (control-plane paths need a countersign or an App receipt).

Why the receipt is a comment and not a formal APPROVE review: GitHub refuses pull-request approvals from `GITHUB_TOKEN` unless the repository setting "Allow GitHub Actions to create and approve pull requests" is enabled, and enabling it lets *every* workflow approve. The comment form needs no setting and is the form the evaluator already verifies by App slug and id.

### How the evaluator selects evidence sources per level

Today `collectEvidence` accepts three forms: a formal review by a listed Bot login (user type `Bot`, exact `commit_id`; no App provenance check, since GitHub exposes none on reviews), a `review-evidence:v1` comment from a listed App (bound by `performed_via_github_app` slug and id), and an `owner-attested-review:v1` comment countersigned by the owner for a vendor with no App presence (`ownerAttestedReview` refuses vendors in `appReviewerVendors`, minus `ownerCountersignVendors` once #534 lands). Today it has no `workflow-review:v1` marker, no run lookup, no notion of a level, and `validateConfig` refuses any key it does not know, so every row and mechanic below is new code. The proposal adds one form and one selector:

| Source | Level 0 | Level 1 | Level 2 | Level 3 |
|---|---|---|---|---|
| `workflow-review:v1` comment from `github-actions[bot]` with a verified `run-id`, job binding and `reviewer-vendor` equal to `reviewerVendor` | counted, informational | **counted**, except on heads touching `.github/workflows/**` or `.agents/gibson-delivery.json` | refused (`identity:workflow-receipt-at-level-2`) | refused |
| Formal review by a listed Bot login at the exact head, or `review-evidence:v1` comment from a listed App (slug + id) | counted, informational | counted if the adopter lists one | **counted** | counted |
| `owner-attested-review:v1` countersign (D-019 rules) | counted, informational | counted | counted | counted |
| Unlisted commit author | resolves to `human` | resolves to `human` | `identity-unresolved` → failure | failure |
| Owner-identity commit, no `Agent-Vendor:` trailer | vendor unknown; any reviewer clears | vendor unknown; any reviewer clears | `independent` reviewer only | `independent` reviewer only |
| Carve-out path touched (control plane, secrets/billing, schema) | named in description | named in description; control-plane paths need a countersign or App receipt (above) | named in description | **provisional (Q8):** requires a reviewer-only (`independent`) identity's pass |
| `review-evidence` in `requiredContexts` | **no** (the adoption flow omits it; `git-configure.sh --audit` reports if branch protection lists it) | yes | yes | yes |

Mechanics, as proposed for the Tier C implementation PR that would follow acceptance:

- The evaluator gains a `--delivery <path>` argument; the workflow passes the trusted checkout's `.agents/gibson-delivery.json`. `reviewPolicy` is validated as strictly as the trust file: `level` an integer 0..3; `reviewerVendor` required at levels 0 and 1 and refused at 2 and 3, and it must be in `attestationVendors` (never `owner`, `unknown`, `independent`, `coderabbit` or `workflow`); `decidedBy.login` equal to the trust file's `ownerLogin` and `decidedBy.date` an ISO date, both required when `level` is below 2; unknown keys refused (`config-error:reviewPolicy:<key>`). **Absent `reviewPolicy`** (or no delivery file) evaluates as level 2, which is the evaluator's behaviour today, so no existing adopter changes rung by omission; the status description then reads "level 2 (unset)". A present but malformed key is `config-error`, not a default.
- A new marker `workflow-review:v1` with fields `head-sha`, `reviewer-vendor`, `result`, `run-id`, registered in `MARKER_FIELDS` so `delivery-receipt.mjs` re-serialises it from those keys only. The identity entry for `github-actions[bot]` carries a new vendor token `workflow`, which is never a same-vendor match on its own; the vendor used for exclusion is the receipt's `reviewer-vendor`, which must be in `attestationVendors`.
- The run binding is two lookups per receipt, `GET /repos/{owner}/{repo}/actions/runs/{run-id}` and `GET .../runs/{run-id}/jobs`, failing closed on API error like every other lookup (`api-error:run-lookup`). Checks are those in point 4 above: repository, fixed `path`, `event` in {`pull_request_target`, `schedule`}, completed with `conclusion: success` at evaluation time, run `created_at` before the comment, a job named `review <pr> <head-sha>`, and for `pull_request_target` runs `head_sha` and `pull_requests[]` matching this head and PR.
- `reviewer-vendor` in the receipt must equal `reviewPolicy.reviewerVendor`; a mismatch is refused with reason `workflow-receipt-vendor-mismatch` (state `failure`: the committed policy and the workflow's output disagree, which is a control-plane fault, not an absence of review).
- Control-plane exclusion at level 1: a head whose files include anything under `.github/workflows/` or `.agents/gibson-delivery.json` treats a `workflow-review:v1` receipt as ineligible (`same-vendor-reviewer` is the wrong token; a new `workflow-receipt-on-control-plane` reason, state `pending`, says what is needed).
- `git-configure.sh`'s allowed-key list for the delivery file gains `reviewPolicy`, and its `--audit` reports a level-0 repository whose branch protection requires `review-evidence` (or a level ≥1 repository whose protection does not) as drift, the same L-004 class it reports today for required-check name drift.
- The status description prefixes every verdict with `level N:`; the delivery receipt (`gibson.delivery.v1`) records the level in force at merge.

### The adoption question

Adoption (today `playbooks/adopt.md` Step 2 and `scripts/git-configure.sh`; `adopt.sh` when the open source readiness work ships it) asks the adopter one question with the Ask Contract and writes the answer into `.agents/gibson-delivery.json`:

| Field | Text |
|---|---|
| What I'm asking | Choose how strictly this project checks that every proposed change was read by a second reviewer before it can be merged. The default is **level 1**. |
| What it does | **Level 1 (default):** every pull request is read by a second AI model that runs in your GitHub Actions and posts a pass or fail; a change cannot merge until a model other than the one that wrote it has passed it. Needs one API key for a model you do not write with. If your project is public on GitHub, it also needs one setting that lets this reviewer run on proposed changes (I will ask for it separately, with what it does and why). **Level 0:** the same reviewer runs and posts its verdict, but nothing blocks a merge. **Level 2:** reviews count only from identities you register as GitHub Apps, so the system can prove which model wrote and which reviewed; set-up takes a day. **Level 3:** level 2 plus the production safeguards (release branch protection, migration checks, post-deploy verification); offered when the delivery-control audit passes. |
| Why | A second reader catches what the author's model is blind to, and the record on each pull request shows who read what. Starting at level 1 means you get that today, and can raise the bar when the project needs it. |
| Risks | Level 1 trusts the author's own declaration of which model wrote the change; a dishonest contributor with write access could obtain a same-vendor second opinion. Level 0 blocks nothing. Both are visible in the project's pull-request history and can be raised at any time with a one-line change that is itself reviewed. Lowering a level later needs the owner's sign-off. |

Level 3 is offered only when `scripts/delivery-control/audit.sh` passes; otherwise the flow says so and offers level 2 with the audit's fix-list.

### Migration of the three existing repositories

## Alternatives rejected

- **One global strictness for every adopter** (today's de facto design). It is this repository's own model exported unchanged, and it is the cause of the one-to-two-day stall. Rejected by Mark's direction.
- **Level 2 as the shipped default.** Same stall, now documented. Rejected.
- **Level 0 as the shipped default.** Nothing enforces Law 5 and the adopter never sees what the gate is for; the first thing they learn about review evidence is that it does nothing. Rejected: the default must block *something* so the mechanism is visible.
- **Choosing the level per pull request** (a label, a trailer, a workflow input, an environment variable). A lane could lower its own bar for its own push. Rejected: policy lives in committed, reviewed configuration read from the default branch, the same rule the local pre-push gate applies to `.fleet-gate`.
- **Putting the level in the trust file** (`config/review-evidence.v1.json`). The trust file is evaluator-shaped (identities and vendors); the level is repository policy, belongs beside `requiredContexts` (level 0 *is* a `requiredContexts` difference), and is read by the preflight and delivery-control scripts that never open the trust file. Rejected; the trust file keeps identities.
- **Having the adopter create a GitHub App at level 1.** App creation is the step the default path exists to remove. Rejected for the default; it is level 2.
- **A formal APPROVE from `github-actions[bot]` as the level-1 receipt.** Needs the repository-wide setting that lets every workflow approve pull requests, and GitHub exposes no App provenance on a review, so the evaluator could bind it only by login. Rejected; the comment receipt needs no setting and is verified by slug, id and run.
- **A configurable reference workflow path.** A committed policy could point level 1 at any workflow able to post the marker, changing what a level-1 pass means with a one-line edit that the level-1 reviewer itself would clear. Rejected; the path is fixed and the file is a control-plane path.
- **Trusting the `reviewer-vendor` written in the comment.** The workflow writes the comment, so the field is only as trustworthy as the workflow file; binding it to committed `reviewerVendor` makes the authorised vendor a reviewed, default-branch fact and turns a disagreement into a fault. Rejected as the sole source.
- **A third-party review service as the level-1 default** (CodeRabbit or a vendor's own connector). A paid or external dependency chosen for the adopter, and a vendor decision this repository has deliberately not made (its CodeRabbit pilot was evidence-gated, never merge-authoritative). Rejected for the default; both remain available as level-2 identities.
- **A continuous score instead of rungs.** Not auditable: a reader of a PR cannot tell what a `0.7` guaranteed. Rejected; each level names a fixed set of guarantees.
- **Reading the level from the PR's own configuration** so the adoption PR can set it before merge. The adoption PR is the one case where the configuration does not exist yet on the default branch, and it is handled by ordering: the install merges under the pre-adoption protection, then `git-configure.sh --apply` makes `review-evidence` required. Rejected: the cost is one merge under the repository's prior rules; the alternative hands every later lane a lever.

## Open questions for Mark

1. **Default = 1.** Is level 1 (second opinion through the reference workflow, no App) the shipped default, as proposed? The alternative with a case is level 0 with the adoption flow nudging to 1.
2. **ProductApp's level.** Confirm 1 (install the reference workflow and one secret) or record 0 explicitly. Today it is 0 in substance.
3. **Lowering a level after D-014.** The ratchet needs the owner's sign-off to loosen; D-014 removed owner attestation, approval and labels from every head. The proposal above is (c): the validator refuses a level below 2 without `reviewPolicy.decidedBy` naming the owner login and a date, and the lowering head cannot be cleared by the workflow receipt. Alternatives: (a) a PR that lowers `reviewPolicy.level` requires the owner's own merge click and nothing else, the one surviving owner action, as D-019's Tier C PR did; (b) a lowering PR is cleared like any other Tier C change (E3 plus required checks) and the owner's sign-off is the merged decision record. (c) is checkable by machine today but only proves the file names the owner; (a) proves the owner acted but only once `merged_by` is recorded. Which rule, or (c) now and (a) when the probe exists?
4. **This repository's own delivery file.** `.agents/gibson-delivery.json` was designed for targets that deploy (`model`, `productionBranch`, `productionEnvironment`). For a library repository with no production, which fields are required and what does `model` say? A `library` model value, or `null`?
5. **TargetApp's evaluator.** Keep the sibling evaluator and trust file (with its `routine` / `schema` / `tier-c-delegated` capabilities) and only declare `level: 3`, or converge on this repository's evaluator so one implementation carries all four levels? Convergence is real work and a Tier C change on a production repository.
6. **Level-1 vendor choice.** The reference workflow calls one model API with one secret. The proposal above requires the reviewer's vendor to differ from every author vendor the head declares, and the workflow declines to review a head whose declared author vendor equals its own; an adopter whose only key is for the vendor they write with is told so in the status and chooses a second key or level 0. The alternative is to accept a same-vendor second opinion (E2 in D-012's taxonomy) at level 1 for that adopter, which widens who can use level 1 at the cost of the cross-vendor promise. Keep the proposal, or accept E2?
7. **Unlisted authors at level 1 resolve to `human`.** This is what lets a solo adopter merge their own commits without listing every contributor. Accept, or require listing at level 1 too?
8. **Level 3 and carve-out paths.** Should a head touching a control-plane, secrets/billing or schema path at level 3 require a pass from a reviewer-only (`independent`) identity rather than any cross-vendor reviewer? It is stricter than any repository enforces today and would make the Tier C floor machine-checked by path.
9. **Canonical path.** `docs/23-delivery-control.md`, `scripts/delivery-control/lib.sh` and `scripts/git-configure.sh` read a root `.gibson-delivery.json` today; `gibson-ship`'s preflight reads `.agents/gibson-delivery.json` today; no adopter has either file. Proposal: `.agents/gibson-delivery.json` becomes canonical (the `.agents/` prefix is already a carve-out pattern, so a change to it is named in every status description) and the root path is read during a deprecation window. Confirm, or keep the root path and move the preflight?
10. **Names.** `solo`, `second-opinion`, `signed-identities`, `delivery-control` are working names. Keep, or rename?
11. **The Actions event policy, for this repository and for public adopters.** This repository's `pr-review-evidence.yml` and the proposed level-1 reviewer both run on `pull_request_target` in public repositories, which GitHub's default policy blocks from 2026-12-02. Set an explicit Actions event policy allowing `pull_request_target` on this repository now (and make it the adoption flow's prerequisite for public adopters), or move the evaluator to its scheduled sweep and accept that level 1 is unavailable to public adopters until the job-name spike proves the scheduled fallback? This is a prerequisite for the shipped default, not a detail.
