# #875 Phase 1.1: contact-spine hardening — live registration gap, collision persistence, write concurrency

## Context

Epic #875's Phase 1 (contact spine) is already shipped — issue #876, PR #882, merged 2026-07-28. This is **not** Phase 1 work. It's a hardening/gap-closure follow-up produced by an adversarial multi-pass review (3 independent implementation plans, cross-examined by 9 skeptical passes across data-loss/collision-safety/rollback-safety lenses, all findings verified against live code) that found the shipped code has real gaps between what #875 asked for and what actually landed — including one that's live in production today.

Full source doc (29K chars, complete schema/algorithm/sequencing spec) available on request; this issue carries the actionable summary and the decisions needed to dispatch it.

## The headline finding

**The two real registration flows — public single-attendee and group/bulk — never call the CRM contact-spine linking function at all.** Only an unused v1 API route does (verified: zero references to `crm`/`Crm`/`contact-spine` in `register/actions.ts`, `register/group/actions.ts`, or `inventory-core.ts`, the shared DB-write helper both flows use). Most real registrations don't enter the CRM until someone manually re-runs the offline backfill script.

Where the spine *is* wired in (the v1 route), a name collision on a shared email still silently links two different humans' registration history under one contact with **zero trace anywhere** — no log, no DB row. Root cause: `ensureCrmContact` does unguarded check-then-create (`findUnique` → `create`, no transaction/upsert/P2002 handling) — a real race condition that can throw unhandled errors on concurrent registrations, and in the backfill script aborts the entire run mid-batch, discarding every collision found before the crash.

## Decisions (confirmed 2026-08-11)

1. **Blank-name collision default:** flag for review (not pass-through).
2. **Sponsor multi-year linking:** "most recent sponsorship wins" — no schema change, no `subjectId` semantic change, no one-time data migration required for already-backfilled rows. (Reverses the doc's recommendation of per-year links; simpler, no migration risk.)
3. **Consent-gate send paths:** verified — `isOutreachOnlyProspectEmail` (`contact-spine.ts`) has zero callers anywhere in the codebase. The three actual recipient-list builders (`broadcast-recipients.ts`, `attendee-messages.ts`, `cfp-comms.ts`) query `Registration`/`EventSponsor`/`VolunteerSignup` directly — imported CRM prospects never appear in their audience queries today because there is no send path that targets `CrmContact` prospects at all yet. **This step is deferred, not built** — there's nothing to wire the gate into until a prospect-outreach send feature exists (Phase 2+ support-desk territory). Leave `isOutreachOnlyProspectEmail` in place with its doc comment as the hard requirement for whoever builds that feature.
4. **Manual merge/split UI:** explicitly deferred, not in this issue's scope. `CrmContactCollision` rows stay accept/reject only; no way to represent "two different people share this email" ships here.
5. **Public registration path wiring:** bundled into this issue (not split out) — consent-gating is moot without it, and the collision-safety fixes need it in scope to be tested end-to-end.
6. Filed as this issue + dispatching to the fleet now (not one or the other).

## Collision-detection algorithm (canonical, applies identically at all four write sites after Step C)

```
flag = false
if incoming has NO firstName AND NO lastName at all:
    if existing.lastName is present:
        flag = true                          # blank-name case — confirmed: flag it
elif existing.lastName present AND incoming.lastName present:
    if existing.lastName != incoming.lastName:
        flag = true
    elif existing.firstName present AND incoming.firstName present:
        if existing.firstName != incoming.firstName:
            flag = true
return flag
```
Comparison case-insensitive, trimmed. Suppression override (group orders, Step E) applies *before* this predicate runs, not inside it. On flag: link still completes (never blocked) — collision row written immediately.

## Test plan (additions beyond what's already covered by existing suites)

- Concurrency: two simulated concurrent `ensureCrmContact` calls for the same `(orgId, email)` — exactly one row, no unhandled exception.
- Group suppression: 5-row group order sharing one email, 5 distinct names — zero collision rows, all 5 link to one contact.
- CSV collision completeness: flagged row's full payload lands in `CrmContactCollision` at apply time; "accept" actually creates the link, not just flips a status.
- PARTNER link event-scoping: same prospect imported into two events → two distinct links; deleting one event leaves the other's link intact.
- Collision dedupe: backfill script run twice against unchanged data → one collision row per collision, not one per run.
- Batch partial-failure isolation: mid-batch CSV failure → rows before the failure stay committed, response reports accurate partial success.
